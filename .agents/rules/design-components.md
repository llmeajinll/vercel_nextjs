# 컴포넌트와 페이지 구조

사용자 제공 「컴포넌트와 페이지 구조 — Components」의 기준이다. 시각 수치는 [기본 규격](design-foundations.md), 적용·우선순위는 [규칙 안내](README.md)를 따른다.

## A. 프로젝트 헤더

다음 순서로 구성한다.

1. 식별 줄: 프로젝트 번호 · 프레임워크 배지 · 프로젝트 종류
2. 프로젝트 제목
3. 파란 프로젝트 부제: `accent`, 20px, 600
4. 소개 한 문단
5. 정보 네 칸: 기간 · 역할 · 인원 · 기여도
6. 배포·GitHub 링크 버튼

- 부제를 회색이나 보통 굵기로 표시하지 않는다.
- 검증 범위·측정 조건·성과 해석은 헤더에 두지 않고, 하단 ‘테스트 및 협업’ 또는 ‘검증’ 영역의 맨 위에 둔다.
- 내용·수치는 실제 프로젝트 데이터에서 가져온다. 첨부 예시의 날짜나 기여도를 다른 프로젝트에 복사하지 않는다.
- `ProjectIntro`, `ProjectIdentity`, `ProjectSubtitle`, `ProjectFacts`, `PillLink`를 조합한다.

## B. 라벨 행과 분류별 기술 스택

- 모든 정보 행은 왼쪽 라벨 영역 240px와 오른쪽 본문으로 구성한다. 본문 읽기 폭은 최대 760px다.
- 기술 스택은 역할별로 분류한 뒤 칩으로 보여준다. 분류 없는 칩 묶음으로 표시하지 않는다.
- 분류 제목은 `dt`, 해당 기술은 `dd`로 구성한다. 예시는 화면·라우팅 / 데이터·상태 / 외부 연동 등이며 프로젝트에 맞게 분류한다.
- 기술 스택은 역할과 담당 업무 다음, 주요 화면·주요 기능 플로우보다 앞에 둔다.
- 정보 행을 h2 섹션 뒤에 이어 붙여 그 섹션의 일부처럼 보이게 하지 않는다.
- `SectionRow`, `Label`, `Chip`과 프로젝트의 `stackGroups`를 사용한다.

## C. 섹션 제목과 사례

- 주요 개발 내용·트러블슈팅은 h2 제목과 사례 개수로 시작한다. 섹션 설명을 읽은 뒤 사례로 이어진다.
- 사례는 왼쪽 번호와 오른쪽 제목·키워드·내용으로 구성한다.
- 사례 제목은 h3, 22px/600/−0.02em이며, 번호는 28px/500/`accent`다.
- 문제·원인·해결·결과 같은 사례 안 소제목은 12px/600/`ink`다. 왼쪽 정보 행 라벨과 혼동하지 않는다.
- 기술적 판단, 상태 이름, 코드 이름, 테스트 근거를 임의로 생략하거나 바꾸지 않는다.
- `Heading`, `TitleBar`, `SectionRow`, `CaseBlock`, `Rich`, `Dashes`를 조합한다.

### 목록

- 1단계 기호는 `–`, 2단계 기호는 `·`를 사용한다.
- 2단계 목록은 15px, `ink-2`로 표시한다. 간격은 기본 규격의 목록 규칙을 따른다.
- 하위 목록을 왼쪽 세로선(`border-left`)으로 묶지 않는다.
- 문장 안 핵심 구절은 `highlight`와 굵게 표시를 함께 사용한다. 전체 문단을 강조로 덮지 않는다.

## D. 표

- 첫 가로선은 1px `ink`, 나머지 행 구분선은 1px `line`이다.
- 머리글은 `ink-3`, 표 본문은 `body-s` 기준으로 읽기 쉽게 정렬한다.
- 텍스트와 수치를 각각의 열에 맞춰 정렬하고, 단위·측정 조건·전후 기준을 명확히 표시한다.
- 좁은 화면에서 표 자체가 가로로 스크롤될 수는 있으나 페이지 전체가 넘치게 하지 않는다.
- 기존 `CaseBlock`의 표 렌더러를 재사용한다.

## E. 노트

- `surface` 배경, 14px 반경, `ink-2` 글자를 사용한다.
- 설명을 보충하는 조건·주의점·성과 해석을 담는다. 새로운 색상이나 그림자로 강조하지 않는다.
- 검증 범위 노트는 테스트·검증 영역의 맨 위에 둔다.
- 기존 `CaseBlock` 노트 또는 `EvidenceNote`의 역할에 맞는 옵션을 사용한다.

## F. 카드와 화면

- 일반 카드는 18px 반경과 `surface` 면을 사용한다. 메인 프로젝트 카드는 28px다.
- 조건 카드의 구조는 항목 이름 → 핵심 값 → 가정·요구 조건 설명이다. 수치를 측정 성과처럼 바꾸지 않는다.
- 화면 이미지의 반경은 18px다. 실제 구현 이미지와 설명을 연결하고 원본의 의미를 유지한다.
- 주요 화면·주요 기능 플로우는 반드시 h2 섹션 제목을 먼저 보여준다. 헤더 바로 아래에 제목 없는 캐러셀을 붙이지 않는다.
- 이미지 확대·캐러셀·슬라이더 데모의 실제 동작, 접근성 이름, 키보드 포커스를 유지한다.
- `SummaryGrid`, `FlowDetail`, `Gallery`, `Zoomable` 등 기존 공통 UI를 사용한다.

## G. 다음 프로젝트

- ‘다음 프로젝트 · 번호’ → 프로젝트 이름 → 이동 표시 순서로 구성한다.
- 프로젝트 이름은 `next-title` 44px/600/−0.03em 기준이다.
- 다음 프로젝트를 누르면 해당 상세 URL로 이동하고, 이 블록 다음에는 공통 푸터가 온다.

## 상세 페이지 순서

| 순서 | 영역 |
| --- | --- |
| 01 | 프로젝트 헤더(A) |
| 02 | 배경 정보 — 배경과 과제·기획·디자인 등 프로젝트에 필요한 내용 |
| 03 | 역할과 담당 업무 |
| 04 | 기술 스택 — 역할별 분류(B). 정보 행은 여기까지 |
| 05 | 주요 화면 또는 주요 기능 플로우 — 있을 때 h2 섹션으로 표시 |
| 06 | 주요 개발 내용 — h2와 사례(C) |
| 07 | 트러블슈팅 — h2와 사례(C) |
| 08 | 테스트 및 협업 또는 검증 — 맨 위에 검증 범위 |
| 09 | 다음 프로젝트(G) → 공통 푸터 |

프로젝트에 없는 섹션은 생략하되, 정보를 새로 만들어 채우지 않는다. 있는 섹션의 상대적인 순서는 위 표를 따른다.

## 금지 사항

- 회색 부제 또는 20px/600/`accent`와 다른 제목 아래 한 줄
- 분류 없이 나열한 기술 스택 칩
- 헤더 안에 둔 검증 범위 문단
- 왼쪽 세로선으로 묶은 하위 목록
- h2 제목 없이 헤더 바로 아래 붙인 화면 캐러셀
- h2 섹션 뒤에 이어 붙여 그 섹션의 일부처럼 보이는 정보 행
- 장식용 그림자, 그라데이션, 두 번째 강조색
- `ink-4`로 표시한 읽어야 하는 글자

현재 코드에서 이 금지 사항을 발견하면 기존 관행으로 인정하지 않는다. 요청한 수정 영역에서 공통 컴포넌트와 함께 고치고, 범위 밖에 남은 차이는 완료 보고에 구분한다.
