# 글쓰기 규칙

포트폴리오 화면 문구(`src/portfolio/data.ts`), 프로젝트 소개, README처럼 프로젝트 밖의 사람이 읽는 글을 쓰거나 고칠 때 적용한다. 사실관계와 기여도 구분은 [공통 작업 규칙](../../AGENTS.md)의 '콘텐츠와 기여도'를 함께 따른다.

## 작업 모델

- 글을 쓰거나 고치는 작업은 Claude Opus 5.5(`claude-opus-5-5`)를 추론 강도 extra high(`xhigh`)로 사용한다.
- 현재 세션의 모델이나 추론 강도가 다르면, 이 조건의 하위 에이전트에 글 작업을 맡기거나 사용자에게 전환을 요청한다.
- Claude를 사용할 수 없으면 Codex `sol6.2`를 추론 강도 extra high(`xhigh`)로 사용한다.

## 독자

- 독자는 이 프로젝트를 처음 보는 한국 사람이다. 개발자일 수도 있고 인사 담당자일 수도 있다.
- 독자는 코드, 회의 내용, 이전 대화를 모른다. 글만 읽고 이해할 수 있어야 한다.
- 인사 담당자는 무엇이 문제였고 무엇이 나아졌는지를, 개발자는 왜 그렇게 판단했는지를 찾는다. 한 사례 안에서 두 질문에 모두 답한다.

## 읽는 화면

- 이 포트폴리오는 프론트엔드 개발자의 포트폴리오다. 글을 읽는 화면도 실력으로 평가받으므로, 읽는 데 불편한 곳이 없어야 한다.
- 문구만 고쳐서 읽기 불편함이 사라지지 않으면 화면 구조도 함께 고친다. 더 나은 읽기 경험이 있으면 새 컴포넌트를 만들어도 된다.
- 새 컴포넌트는 공통 UI(`src/portfolio/ui/`)에 두고 [디자인 규칙](README.md)의 역할과 수치를 따른다. 같은 역할의 컴포넌트가 이미 있으면 먼저 그 컴포넌트에 옵션을 더한다.
- 글이나 화면을 고친 뒤에는 반드시 Playwright로 실제 화면을 캡처해 확인한다. 데스크톱 1440px과 모바일 390px에서 줄바꿈, 문단 길이, 읽는 순서, 가로 넘침을 보고, 캡처로 확인한 내용을 완료 보고에 적는다.

## 분량은 이해를 기준으로 정한다

- 짧게, 상세하게, 쉬운 단어로 썼다고 이해하기 쉬운 글이 되지는 않는다. 문장 사이의 연결을 잘라 내면 짧아도 읽히지 않는다.
- 독자가 모르는 전제가 있으면 문장을 더 써서 먼저 설명한다. 독자가 이미 알 만한 내용과 같은 말의 반복은 줄인다.
- 처음 읽는 사람이 멈추지 않고 다음 문장으로 넘어갈 수 있는지로 분량을 판단한다. 문장 수나 글자 수를 목표로 삼지 않는다.
- 글이 한 덩어리로 길어지면 줄이기보다 역할(상황·판단·근거 등)로 나눈다. 과정이 복잡해 글보다 그림이 빠르면, 그림이 필요한지 사용자에게 묻는다.

## 사례에 들어가야 할 내용

상황·판단·근거, 문제·원인·해결·결과 등 형식과 관계없이 다음 네 가지가 빠지면 안 된다.

| 내용 | 확인 질문 |
| --- | --- |
| 장면 | 사용자가 무엇을 하던 중이었나? |
| 손해 | 그대로 두면 누가 무엇을 잃나? "알 수 없습니다", "보게 됩니다"에서 끝나지 않았나? |
| 판단 | 누가(화면·서버·사용자) 무엇을 다르게 하게 했나? |
| 근거 | 그 판단으로 왜 손해가 사라지나? 판단 문장을 다시 말하고 있지 않나? |

- 근거는 판단이 문제를 해결하는 이유다. 테스트 결과는 근거가 아니라 결과·검증 영역에 쓴다.
- 서버가 하는 일과 화면이 하는 일을 섞지 않는다. Nova의 순번 관리는 서버 역할이다.
- 테스트 ID, 내부 파일명, 시나리오 번호를 본문에 쓰지 않는다. 어떤 상황을 확인했고 결과가 어땠는지를 말로 쓴다.

## 용어와 코드 이름

- 처음 나오는 개념은 쉬운 말로 먼저 풀고, 코드 이름은 괄호에 붙인다. 예: "`RootLayout`이 맡게 했습니다" → "여러 페이지가 함께 쓰는 바깥 틀(`RootLayout`)이 맡게 했습니다"
- 괄호 속 코드 이름을 지우고 읽어도 문장이 통해야 한다. 인사 담당자는 괄호를 건너뛰고, 개발자는 괄호로 실제 구현을 확인한다.
- 코드 이름과 상태 이름은 지우거나 바꾸지 않는다. 읽는 순서만 풀이 뒤로 옮긴다.
- 같은 대상은 글 전체에서 같은 말로 부른다. 입장권·토큰·티켓처럼 섞어 부르지 않는다.
- 영문 상태값을 우리말로 옮길 때는 코드와 데이터에서 실제 의미를 확인한다. 예: Nova의 `CLOSED`는 사유가 `NOT_IN_QUEUE`이면 다시 진입하므로, '마감'이라고만 옮기면 틀린다.

## 문장

jobstack의 자기소개서·포트폴리오 첨삭 기준을 따른다. Claude Code에서는 `/jobstack` 스킬로 점검할 수 있지만, 이 목록만으로도 같은 기준을 적용할 수 있어야 한다.

- 합니다체로 쓴다. 직접적이고 구체적으로 쓰고, 빈말 대신 근거와 예시를 든다. '~을 통해', '~에 있어서', '~하는 것이 가능합니다' 같은 번역투와 과한 격식을 피한다.
- 주어를 밝힌다. 화면, 서버, 사용자 중 누가 하는 일인지 문장만 보고 알 수 있어야 한다.
- 한 문장에는 한 가지 판단만 담는다. 쉼표가 3개 이상이거나 '그리고·또한·이를 통해·그 결과'가 2개 이상 이어지면 나눈다. 나눌 때는 무엇을 했나 → 왜 했나 → 결과는 순서로 역할을 나눈다.
- 문제·역할·행동·결과를 한 문장에 섞지 않는다. 팀의 성과와 본인의 몫도 한 문장에 섞지 않는다.
- '다각적·포괄적·심층적·혁신적·체계적', '다양한', '많은 것을 배웠습니다', 본인 몫이 없는 '기여했습니다'는 쓰지 않는다.
- '개선했습니다', '향상시켰습니다'에는 전후 비교나 범위를 붙인다. 측정하지 않았으면 무엇이 달라졌는지를 말로 쓰고, 수치를 만들지 않는다.
- '급변하는', '디지털 전환의 시대'처럼 시대·산업 일반론으로 시작하지 않는다.
- 프로젝트 이름을 다른 프로젝트로 바꿔도 그대로 성립하는 문장은 구체성이 없다. 이 프로젝트에서만 성립하는 조건·수치·판단으로 바꾼다.

## 다 쓴 뒤 다시 읽기

글을 고친 뒤 바로 끝내지 않는다. 프로젝트를 모르는 독자라고 생각하고 처음부터 다시 읽는다.

1. 문장마다 "그래서 어쩌라고?", "그게 뭔데?", "그게 왜 문제인데?"라는 질문이 생기는지 확인한다. 질문이 생기면 그 자리에 빠진 내용이 있다.
2. 빠진 내용은 추측으로 채우지 않는다. 이 저장소의 `src/portfolio/data.ts`·`docs/`·이미지 캡션을 먼저 찾고, 이어 해당 프로젝트의 GitHub·배포 링크(`links`)와 README를 확인한다.
3. 그래도 확인되지 않으면 사용자에게 묻는다. 어느 문장에서 무엇이 빠졌는지를 함께 적는다.
4. 고친 뒤 1번부터 다시 읽는다. 더 이상 질문이 생기지 않을 때 끝낸다.
5. Playwright 캡처로 실제 화면에서 한 번 더 읽는다. 파일에서는 괜찮던 글도 화면에서는 한 덩어리로 보이거나 줄바꿈이 어색할 수 있다.
6. 완료 보고에 확인한 출처와, 확인하지 못해 남긴 질문을 적는다.

## 예시

사용자가 "처음 보는 사람은 이게 무슨 말인지 모른다"고 지적한 Nova 대기열 문구다.

### 고치기 전

> **대기 중에 다른 페이지로 이동해도 순번이 끊기지 않게**
>
> 상황 — 순번 조회를 상품 페이지에서 하면, 다른 페이지로 이동하는 순간 조회도 함께 멈춥니다. 서버는 조회가 끊긴 지 250초가 지나면 사용자를 대기열에서 뺍니다.
>
> 판단 — 상품 페이지는 대기열 진입만 요청하고, 순번 조회는 모든 페이지에 공통으로 들어가는 레이아웃(RootLayout)의 대기열 컴포넌트가 맡게 했습니다.
>
> 근거 — 레이아웃은 페이지를 옮겨도 해제되지 않습니다. 그래서 대기창을 닫거나 다른 상품을 보는 동안에도 조회가 이어져, 250초 기준에 걸려 줄에서 빠지지 않습니다.

- 짧지만 '순번 조회'가 무엇인지, 누가 하는지 설명이 없다.
- 사용자가 기다리다가 왜 다른 페이지로 가는지, 장면이 없다.
- 서버가 250초 뒤에 사용자를 빼는 이유가 없어 규칙이 임의로 보인다.
- 사용자가 무엇을 잃는지(기다리던 자리)가 없다. 읽고 나면 "그래서 어쩌라고?"가 남는다.
- 판단이 레이아웃·컴포넌트 같은 구조 이름으로 채워져 있어 인사 담당자는 따라올 수 없다.

### 고친 뒤

> **기다리는 동안 다른 상품을 둘러봐도 자리를 잃지 않게**
>
> 상황 — 사전예약이 열리면 사용자는 대기열에서 차례를 기다립니다. 기다리는 동안 화면은 일정한 간격으로 서버에 지금 몇 번째인지 묻습니다. 서버는 250초 동안 이 질문이 없으면 사용자가 대기를 그만둔 것으로 보고 대기열에서 뺍니다. 그런데 이 질문을 상품 페이지가 맡으면, 사용자가 다른 상품을 보러 가는 순간 질문도 멈춥니다. 사용자는 계속 기다리는 중인데도 250초가 지나면 기다리던 자리를 잃습니다.
>
> 판단 — 순번을 묻는 일을 상품 페이지에서 떼어 내, 여러 페이지가 함께 쓰는 바깥 틀(`RootLayout`)에 맡겼습니다.
>
> 근거 — 바깥 틀은 그 안에서 페이지를 옮겨 다녀도 사라지지 않습니다. 그래서 대기창을 닫거나 다른 상품을 보는 동안에도 화면이 계속 순번을 묻고, 서버는 사용자가 아직 기다리고 있다고 판단합니다. 사용자도 화면 상단에서 자기 순번을 계속 확인할 수 있습니다.

- 장면 → 서버의 규칙과 그 이유 → 사용자가 잃는 것 → 누가 무엇을 바꿨는지 → 왜 해결되는지 순서로 읽힌다.
- 고치기 전보다 길어졌지만, 처음 보는 독자가 멈추는 곳이 없다.
- `RootLayout`은 풀이 뒤 괄호에 남겨, 개발자가 실제 구현을 찾을 수 있다.
- 고친 문장의 사실은 `src/portfolio/data.ts`의 Nova 데이터에서 확인했다. 고치기 전의 '상품 페이지는 대기열 진입만 요청'은 현재 데이터로 확인되지 않아 넣지 않았다.

### 같은 글에서 보이는 다른 실수

| 고치기 전 | 문제 | 고치는 방법 |
| --- | --- | --- |
| 창마다 새 키를 만들면, 서버는 같은 신청인지 알 수 없습니다. | '키'가 설명 없이 나오고, 그래서 생기는 손해가 없다 | 키가 무엇인지 먼저 풀고, 그대로 두면 예약이 두 건 생길 수 있다고 쓴다 |
| 입장권을 SHA-256으로 변환한 값을 멱등키(Idempotency-Key)로 써서 | 입장권이 무엇인지 설명이 없고, 기술 이름이 문장 앞에 몰려 있다 | '차례가 온 사용자에게 서버가 발급하는 입장권'을 먼저 설명하고, 멱등키·SHA-256은 괄호나 문장 끝에 둔다 |
| 순번 조회가 일시적으로 실패했을 때 대기열을 비우면 | 누가 비우는지 주어가 없다 | '화면이 대기 정보를 지우면'처럼 주어를 밝힌다 |
| 서버가 마감(CLOSED)을 알려 줄 때만 | 상태값을 실제 의미와 다르게 옮겼다 | '서버가 판매가 끝났다고 알려 주면 대기를 끝내고, 대기열에 없다고 알려 주면 다시 줄을 섭니다'처럼 사유별로 쓴다 |
| 새로고침하면 브라우저에 저장해 둔 정보만 남습니다. | 어떤 정보인지 없어 다음 문장을 따라갈 수 없다 | '어떤 상품을 기다리고 있었는지에 관한 정보'처럼 구체적으로 쓴다 |
